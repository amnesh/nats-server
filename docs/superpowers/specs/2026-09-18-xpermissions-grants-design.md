# Design: Scoped Resource Permission Groups

- **Date:** 2026-09-18
- **Status:** Draft for fork-owner review; no implementation exists yet.
- **Component:** account JWT scoped signing-key templates and server permission compilation
- **Supersedes:** `2026-09-17-permission-template-macros-design.md` and
  `2026-09-17-permission-template-macros-v2-design.md` as the design authority
  for the next implementation. Those files remain historical descriptions of
  the whole-entry macro implementation until it is replaced.

## 1. Goal and constraints

Resource roles are sets of publish and subscribe subjects, not subject values.
They therefore belong in structured resource groups rather than inside
`pub.allow`, `pub.deny`, `sub.allow`, or `sub.deny`.

This change adds one server-owned extension to a scoped `UserScope.Template`:

```text
nats.signing_keys[].template.xpermissions
```

It is deliberately additive. Standard `pub`, `sub`, `resp`, limits, bearer and
proxy flags, and allowed connection types stay in the typed JWT template and
keep their current meaning. The server adds subjects generated by resource
entries to the standard allow lists. It never removes or overrides a standard
deny.

The implementation is confined to this repository. It does not change the
`nats-io/jwt` dependency or NATS clients. The JWT-producing system must sign
arbitrary JSON because the typed JWT library does not expose `xpermissions`.

## 2. Wire format

`xpermissions` may contain the four resource group fields `kv`, `obj`,
`stream`, and `consumer`, plus the boolean `jsinfo`. Every supplied resource
group must be a nonempty array. `jsinfo: true` adds local account-level info;
`false` adds nothing. Presence of `jsinfo` with either boolean value satisfies
the recognized-field requirement and may appear alone. `jsinfo: false` is
permission-equivalent to omitting the extension. `null`, `{}`, an empty supplied
group, an unknown field, and the former `grants` field are errors; there is no
alias for the old draft schema.

```json
{
  "nats": {
    "signing_keys": [
      {
        "kind": "user_scope",
        "key": "ABCD_SCOPED_SIGNER_PUBLIC_KEY",
        "role": "orders-worker",
        "template": {
          "pub": {
            "allow": ["audit.{{tag(team)}}"],
            "deny": ["$JS.API.STREAM.DELETE.>"]
          },
          "sub": {
            "allow": ["_INBOX.>"]
          },
          "xpermissions": {
            "kv": [
              {"op": "rw", "bucket": "{{tag(kv)}}"}
            ],
            "consumer": [
              {
                "op": "ro",
                "stream": "orders_{{tag(region)}}",
                "consumer": "{{name()}}",
                "domain": "hub"
              }
            ],
            "jsinfo": true
          }
        }
      }
    ]
  }
}
```

The extension parser is strict. It rejects unknown fields, duplicate JSON
members, wrong JSON types, missing fields, extra fields, and unknown or
case-variant `op` values. Group and operation names are the exact lowercase
enums in §3.

The compiler ignores JSON object member order. It processes resource groups in
the fixed order `kv`, `obj`, `stream`, `consumer`, followed by `jsinfo`; preserves
entry order within each group; resolves selectors in the field order listed in
§3; preserves value order from each operation; and deduplicates generated
subjects in first-seen order. Authorization does not depend on output order.

Each resource selector and optional `domain` is one JSON string. It may be a
literal or may contain the existing ordinary value operations:

```text
{{name()}}                 {{subject()}}
{{account-name()}}         {{account-subject()}}
{{tag(key)}}               {{account-tag(key)}}
```

Operations are composable inside the string, for example
`"team_{{tag(team)}}_{{tag(kv)}}"`. Each tag occurrence may yield several
values; the server emits the Cartesian product across all operations and all
selector fields. A selector cannot contain an old resource call such as
`{{kvrw(...)}}`; resource operations cannot be nested.

Every resolved resource and domain value must match `[A-Za-z0-9_-]+`. The
literal string `"*"` is also accepted as the complete `bucket`, `stream`, or
`consumer` value, matching the old positional macro rule. It is rejected in
`domain`, inside a larger string, and when produced by any value operation.
`>` and prefix wildcards such as `team-*` are always rejected.

## 3. Groups, operations, and fields

`domain` is optional on every entry. Every other field shown is required, and
every field not shown for that group is an error. Selector resolution order is
`bucket, domain` for `kv` and `obj`; `stream, domain` for `stream`;
and `stream, consumer, domain` for `consumer`.

| Group | `op` | Required resource fields | Existing profile represented | Generated publish allow | Generated subscribe allow |
|---|---|---|---|---|---|
| `kv` | `ro` | `bucket` | `kvro` | read on `KV_<bucket>` | `$KV.<bucket>.>` |
| `kv` | `rw` | `bucket` | `kvrw` | read + write + KV data | `$KV.<bucket>.>` |
| `kv` | `admin` | `bucket` | `kvadmin` | read + write + KV data + admin | `$KV.<bucket>.>` |
| `obj` | `ro` | `bucket` | `objro` | read on `OBJ_<bucket>` | `$O.<bucket>.>` |
| `obj` | `rw` | `bucket` | `objrw` | read + write + Object data | `$O.<bucket>.>` |
| `obj` | `admin` | `bucket` | `objadmin` | read + write + Object data + admin | `$O.<bucket>.>` |
| `stream` | `ro` | `stream` | `jsread` | read | none |
| `stream` | `admin` | `stream` | `jsadmin` | read + write + admin | none |
| `consumer` | `ro` | `stream`, `consumer` | `jsconsumer` | consumer use | none |
| `consumer` | `admin` | `stream`, `consumer` | `jsconsumeradmin` | consumer use + consumer admin | none |

There is no `stream` `rw`, no `consumer` `rw`, and no other operation alias.
`jsinfo` is not a group: it is a boolean sibling of the four resource groups.
Either boolean value may be the only field in `xpermissions`. `true` generates
the existing local account-level info set once; `false` or omission generates
nothing. Because the extension is additive, `false` never removes or denies
info subjects supplied by a resource group or standard `pub.allow`. It has no
selector and cannot carry a domain.

The operation labels name established subject bundles. `consumer` `ro` means
use an existing consumer, including pull requests, ACKs, and flow control;
`admin` adds that consumer's lifecycle subjects. `stream` `ro` retains the
legacy `jsread` bundle, including consumer create, inspect, list, delete, pull,
ACK, and flow-control helper subjects. Therefore `ro` does not mean that every
generated subject is a subscribe subject or that every API operation is
read-only.

The bundles below are exactly the current sets in
`server/auth_perm_macros.go:115-188`. `{api}` is `$JS.API` locally and
`$JS.<domain>.API` with a domain. `{dom}` is `*` locally and the domain value
when supplied.

**read**

```text
{api}.STREAM.INFO.{stream}
{api}.STREAM.MSG.GET.{stream}
{api}.DIRECT.GET.{stream}
{api}.DIRECT.GET.{stream}.>
{api}.CONSUMER.CREATE.{stream}
{api}.CONSUMER.CREATE.{stream}.>
{api}.CONSUMER.DURABLE.CREATE.{stream}.>
{api}.CONSUMER.INFO.{stream}.>
{api}.CONSUMER.NAMES.{stream}
{api}.CONSUMER.LIST.{stream}
{api}.CONSUMER.DELETE.{stream}.>
{api}.CONSUMER.MSG.NEXT.{stream}.>
$JS.ACK.{stream}.*.*.*.*.*.*
$JS.ACK.{dom}.*.{stream}.*.*.*.*.*.>
$JS.FC.{stream}.*.*
$JS.FC.{dom}.*.{stream}.*.*
```

**write** adds `{api}.STREAM.PURGE.{stream}`. Bucket `rw` and `admin` entries
also add `$KV.<bucket>.>` or `$O.<bucket>.>` as a publish subject. With a
domain, KV data publish becomes `$JS.<domain>.API.$KV.<bucket>.>`; Object Store
data publish remains `$O.<bucket>.>`. Bucket subscribe subjects remain
account-local.

**admin** adds:

```text
{api}.STREAM.CREATE.{stream}
{api}.STREAM.UPDATE.{stream}
{api}.STREAM.DELETE.{stream}
{api}.STREAM.MSG.DELETE.{stream}
{api}.STREAM.SNAPSHOT.{stream}
{api}.STREAM.RESTORE.{stream}
{api}.INFO
```

**account-level info** from `jsinfo: true` is local only:
`$JS.API.INFO`, `$JS.API.STREAM.NAMES`, and `$JS.API.STREAM.LIST`. It does not
infer a domain from any resource entry and never emits a `$JS.*` wildcard.
Domain-specific info remains expressible with those three
`$JS.<domain>.API...` subjects in ordinary `pub.allow`; ordinary value
templates may compose the domain there.

**consumer use** is:

```text
{api}.STREAM.INFO.{stream}
{api}.CONSUMER.INFO.{stream}.{consumer}
{api}.CONSUMER.MSG.NEXT.{stream}.{consumer}
$JS.ACK.{stream}.{consumer}.*.*.*.*.*
$JS.ACK.{dom}.*.{stream}.{consumer}.*.*.*.*.>
$JS.FC.{stream}.{consumer}.*
$JS.FC.{dom}.*.{stream}.{consumer}.*
```

**consumer admin** adds:

```text
{api}.CONSUMER.CREATE.{stream}.{consumer}
{api}.CONSUMER.CREATE.{stream}.{consumer}.>
{api}.CONSUMER.DURABLE.CREATE.{stream}.{consumer}
{api}.CONSUMER.DELETE.{stream}.{consumer}
{api}.CONSUMER.PAUSE.{stream}.{consumer}
{api}.CONSUMER.UNPIN.{stream}.{consumer}
{api}.CONSUMER.RESET.{stream}.{consumer}
```

A bucket value of `*` intentionally gives the API patterns a whole stream-token
wildcard, so it grants the API of every stream in the account, not only bucket
streams. This preserves existing behavior and must remain explicit in operator
documentation.

## 4. Compilation and permission semantics

For a scoped user, the server validates the user against the typed scope, then
compiles permissions into local copies. It expands ordinary template entries,
resolves every resource entry, generates allow subjects, appends them to the
direction defined by the operation, and deduplicates in the deterministic order
from §2. Nothing is installed into the user claim until the complete compile
succeeds.

A required selector that resolves to no values is an authentication error. An
invalid resolved value, undefined operation, arithmetic overflow, or expansion
limit violation is also an authentication error. A resource entry can therefore
never silently disappear.

The existing 4096 expansion cap remains per permission list. Standard template
expansion and grouped entries share the generated-subject budget for
`pub.allow` and for `sub.allow`; deny lists retain their independent existing
budgets. Cartesian sizes are checked before multiplication or allocation.
Candidate generation is bounded before deduplication so duplicates cannot
consume unbounded work.

Standard denies are preserved and the normal permission engine makes them win
over all generated allows. `resp` and every standard limit remain unchanged.
An explicit deny `>` is a real policy rule and is never removed as though it
were the synthetic empty-expansion guard.

The current fail-closed rule is evaluated after ordinary and generated allow
subjects are combined: if a direction had an explicit standard allow entry but
the final combined allow list is empty, add the existing synthetic deny `>`.
A valid generated allow in that direction prevents the guard from blocking it.
This keeps the behavior implemented around `server/auth.go:630-654` while
allowing grouped entries to contribute to the result.

Grouped entries do not change an untouched direction. In particular, a
publish-only `stream` or `consumer` entry, or `jsinfo: true`, leaves an empty
standard subscribe permission under existing NATS semantics, including the
existing meaning of a deny-only subscribe policy. There is no blanket deny for the other
direction.

No operation automatically grants `_INBOX.>` or a delivery subject. When an
allow list restricts subscriptions, the template author must explicitly add
inbox and delivery subjects needed by the client. This is especially relevant
to publish-only groups and to bucket groups, whose generated bucket subscribe
allow turns the subscribe side into an allow list.

When `xpermissions` is absent, all non-resource template behavior is unchanged.
When present, it must contain at least one nonempty resource group or the
`jsinfo` field with a boolean value, as defined in §2.

## 5. Trust, loading, and updates

The server decodes `xpermissions` from the raw account JWT only after
`verifyAccountClaims` has verified the signature, trusted issuer, typed account
claim, and typed validation (`server/server.go:2203-2217`). It correlates each
raw `user_scope` object with the typed scope by the exact signer `key`. Duplicate
signer keys, a raw/typed kind or key mismatch, or an ambiguous scope is an
account-claim error.

Validated resource groups are stored on the `Account`, keyed by scoped signer.
Their authority is therefore the verified account JWT plus the exact signer
that issued the user JWT. A user JWT and an auth-callout response cannot supply
or replace them. Scope and extension must be read under one account read lock so
a connection cannot combine generations.

Initial resolver load, system-account load, resolver/event update, reload, and
incomplete-account refresh must all carry the verified raw extension through
the same install path. Typed-only `UpdateAccountClaims` calls carry no signed
raw extension and must clear any previously stored groups rather than retain
stale authority. The typed scope map and extension map are swapped together
under `Account.mu`; any error leaves the old generation intact.

Extension-only changes count as scoped-signer changes. The existing altered
scope invalidation must close users issued by that signer so reconnect compiles
the new policy. Both normal operator authentication (`server/auth.go:1043-1058`)
and operator auth callout (`server/auth_callout.go:229-242`) use the same atomic
scope-plus-extension lookup and compiler.

The current JWT library ignores unknown `template` fields. Older servers may
therefore ignore `xpermissions`, and an otherwise empty standard permission
set means unrestricted NATS access on those servers. Every server that can
serve the account must be upgraded before an account JWT containing this
extension is installed. This design adds no compatibility guard or fallback
policy rewrite.

## 6. Clean-break migration

All old resource profile calls are rejected in every standard subject list:
`pub.allow`, `pub.deny`, `sub.allow`, and `sub.deny`. Ordinary value operations
remain valid and composable in those lists.

Old duplication:

```json
{
  "pub": {"allow": ["{{kvrw(tag(kv))}}"]},
  "sub": {"allow": ["{{kvrw(tag(kv))}}", "_INBOX.>"]}
}
```

New representation:

```json
{
  "sub": {"allow": ["_INBOX.>"]},
  "xpermissions": {
    "kv": [
      {"op": "rw", "bucket": "{{tag(kv)}}"}
    ]
  }
}
```

A composable selector that was impossible in the old whole-entry grammar is:

```json
{"op": "rw", "bucket": "team_{{tag(team)}}_{{tag(kv)}}"}
```

The last object is an entry in the `kv` array. Local `{{jsinfo()}}` becomes
`"jsinfo": true`. A domain-specific info macro moves to ordinary publish
allows because the boolean never infers or accepts a domain:

```json
{
  "pub": {
    "allow": [
      "$JS.{{tag(js-domain)}}.API.INFO",
      "$JS.{{tag(js-domain)}}.API.STREAM.NAMES",
      "$JS.{{tag(js-domain)}}.API.STREAM.LIST"
    ]
  }
}
```

There is no compatibility mode. Account JWT authors must migrate all resource
macros before deploying the implementation. Ordinary subject templates such as
`"events.{{tag(team)}}.>"` need no change.

## 7. Error behavior

Static schema errors, invalid literals, duplicate or ambiguous scopes, and old
resource macros reject account claim load or update before mutation. Errors
that depend on a user claim—missing tags, invalid resolved values, excessive
Cartesian products, or too many generated subjects—reject that user's
authentication. Logs identify the signer, group, entry index, operation, and
field but must not expose JWT seeds or credentials.

Compilation is atomic. It returns either the complete standard-plus-grouped
permission set or an error; it never installs a prefix of any group and never
partially updates an account.

## 8. Test plan

- Sign raw account JWT fixtures containing the extension; prove typed decoding
  still preserves the normal scope and raw extraction binds the extension to
  the verified account and signer.
- Exercise both ordinary operator user authentication and operator auth-callout
  scoped users. A user-issued extension must have no effect.
- Assert exact local and domain subject sets for all ten resource
  group/operation combinations plus the local-only `jsinfo: true` set,
  including KV versus Object Store data handling and subscribe directions.
- Verify fixed `kv`, `obj`, `stream`, `consumer`, `jsinfo` processing order
  independent of JSON key order, plus entry order, selector value order,
  Cartesian products, stable deduplication, literal `*`, and the 4096 per-list
  cap with overflow-safe preflight.
- Cover every ordinary selector operation, embedded operations, multiple tag
  values, and multi-field Cartesian products.
- Prove explicit pub/sub denies override generated allows, response permissions
  and limits survive unchanged, publish-only groups leave subscribe semantics
  untouched, and explicit inbox and delivery rules remain necessary.
- Prove an ordinary allow that resolves empty still fails closed, while a valid
  grouped entry in that direction is not blocked by the synthetic guard.
- Reject null, empty and malformed extensions; empty or unknown groups;
  `jsinfo` with a non-boolean value; the unsupported `grants` field; unknown
  operations; missing or extra entry fields; wrong types; invalid literals or
  resolved values; wildcard domains; unresolved required operations; duplicate
  signers; and every old resource macro in each of the four standard subject
  lists.
- Prove `jsinfo: true` emits only the local three-subject set, `false` is valid
  alone and adds nothing, and `false` leaves all permissions from resource
  groups and standard `pub.allow` unchanged, including overlapping info
  subjects. Remote-domain info works only through explicit ordinary
  `pub.allow` entries.
- Cover first load, system-account load, extension-only update, resolver/event
  refresh, incomplete-account refresh, typed-only update clearing stale groups,
  atomic rollback on error, and disconnection of clients for altered scopes.

## 9. Risks and non-goals

The generated sets deliberately retain the current profiles' breadth. The
`stream` `ro` set can create and delete consumers on its stream, and a bucket
wildcard grants all stream APIs. This design does not narrow or add powers.

Operation definitions must have one source of truth so subject-set fixes cannot
diverge between tests and grouped compilation. Other non-goals are deny groups,
server-config policy, moving standard permission fields into the extension,
new response or inbox privileges, new operations, client changes, JWT
dependency changes, support for old resource-macro syntax, and safe
mixed-version rollout.
