# NCDL leaf subject routing: official NATS evidence

Status: research note, not an accepted design. Verified 2026-09-18 against upstream NATS Server v2.14.4 (`bbd6dc5`) and current official NATS documentation. The NCDL controller/runtime currently pin the fork at v2.14.1; the relevant `StreamSource.SubjectTransforms` and `RePublish` fields are present in that tag too. [v2.14.1 source fields](https://github.com/nats-io/nats-server/blob/cb557cd5d3ee8b4a253071d9923730d7d5588f99/server/stream.go#L180-L184), [v2.14.1 stream source](https://github.com/nats-io/nats-server/blob/cb557cd5d3ee8b4a253071d9923730d7d5588f99/server/stream.go#L406-L423)

## Problem

NCDL needs to route an edge message such as `evt.>` into a device-scoped hub subject such as `dev.<XUID>.evt.>` without breaking existing local subscribers, and it needs data created during a disconnected interval to arrive after reconnection. Those are two separate requirements: subject rewriting and durable catch-up.

## Findings

### Leaf remotes do not provide a user subject transform in v2.14.4

The v2.14.4 `RemoteLeafOpts` fields include account binding, permissions, compression, isolation, disabling, and discovery behavior, but no subject transform. The complete `parseRemoteLeafNodes` switch likewise accepts no transform key. A leaf remote therefore cannot be configured to rewrite arbitrary user subjects in this release. [v2.14.4 remote type](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/opts.go#L247-L320), [v2.14.4 remote parser](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/opts.go#L3050-L3262)

NATS 2.14.0 added the ability to add and remove leaf remotes at runtime through configuration reload. It did not make every field of an existing remote reloadable. In v2.14.4, an in-place remote change is accepted only for the listed compression, disabled, and TLS fields; changing `isolate` or `request_isolation` on a matched remote fails reload. [v2.14.0 release notes](https://github.com/nats-io/nats-server/releases/tag/v2.14.0), [v2.14.4 reload comparison](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/reload.go#L921-L1057)

Isolation is also distinct from rewriting: it suppresses east-west leaf subscription interest. A later 2.15 change fixed lost leaf-origin information across cluster routes, so v2.14.4 should not be assumed to isolate correctly across a multi-node hub cluster. [leaf isolation configuration](https://docs.nats.io/reference/config/leafnodes/), [2.15 clustered isolation fix](https://github.com/nats-io/nats-server/pull/8504)

### Account mapping changes local delivery

An account mapping rewrites a subject before the server looks for subscribers. A complete mapping from the original subject to a device-prefixed subject therefore makes subscribers on the original subject silent; mappings are account-scoped, not leaf-link-scoped. This conflicts with preserving existing local `evt.>` subscribers unless the contract is deliberately changed or traffic is duplicated by another mechanism. [official mapping semantics](https://docs.nats.io/learn/core-nats/subject-mapping#rename-a-subject), [official mapping pitfalls](https://docs.nats.io/learn/core-nats/subject-mapping#pitfalls)

There is a second leaf-specific boundary to enforce. The server advertises permitted account-mapping sources and real local subscriptions as leaf interest. With an inbound `dev.<XUID>.evt.>` to `evt.>` mapping and local `evt.>` interest, both forms can otherwise cross the link. Use leaf `deny_imports`/`deny_exports` to block raw `evt.>` in the forbidden direction while allowing the namespaced wire subject. v2.14.4 applies the mapping before dispatch but checks leaf permissions against the saved original wire subject, so the namespaced message can pass and then map locally while raw traffic is rejected. [mapping and saved wire subject](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/parser.go#L518-L540), [leaf interest advertisement](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/leafnode.go#L2440-L2563), [wire-subject permission check](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/leafnode.go#L3347-L3441)

### JetStream republish is post-store, live fan-out

`RePublish` runs after a successful stream write and publishes to a Core NATS destination. The official docs describe destination subscribers receiving newly appended messages in real time. It is therefore useful for live server-side fan-out, including a mapping such as `evt.>` to `dev.<XUID>.evt.>` after validation, but it is not a historical replay mechanism for subscribers that were absent or disconnected. [republish documentation](https://github.com/nats-io/nats.docs/blob/f115becf6563e3bbe16bb94cbf87bfceb84199c1/nats-concepts/jetstream/streams.md#L209-L219), [v2.14.4 configuration and commit semantics](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/stream.go#L74-L184), [v2.14.4 store-then-republish path](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/stream.go#L6980-L7145)

That limitation is relative to the stream carrying the republish setting. When a hub target catches up from a source, each recovered message is a new append to the target; a republish setting on that target emits those sourced messages after the hub stores them. NATS 2.10 explicitly broadened republish on sourcing streams to include all sourced messages. A source by itself only stores records and does not create a Core NATS delivery. [NATS 2.10 stream improvement](https://github.com/nats-io/nats.docs/blob/f115becf6563e3bbe16bb94cbf87bfceb84199c1/release_notes/whats_new_210.md#improvements)

### A hub source provides retry and catch-up

A hub stream can source an edge stream across a JetStream domain and apply `subject_transforms`, combining filtering and renaming in one source entry. The target may be created while the origin or route is unavailable; it retries source-consumer setup and resumes from its remembered source position. Replication is asynchronous, so `lag` and last-seen state must be monitored. Do not delete and recreate the origin stream during normal recovery because the source tracks its sequence. [mirror/source behavior](https://docs.nats.io/learn/jetstream/mirrors-and-sources#filters-transforms-and-reach), [classic source protocol, retries, and sequence constraint](https://github.com/nats-io/nats.docs/blob/f115becf6563e3bbe16bb94cbf87bfceb84199c1/using-nats/jetstream/nats_api_reference.md#L100-L124)

Catch-up only covers data the edge stream still retains. A memory-backed capture stream does not provide disk persistence, and `MaxAge` deletes messages after that age. Therefore memory storage or a short age limit cannot satisfy recovery from a process loss or partition longer than the retention window. This is an architectural inference from the documented storage and retention semantics. [storage and age behavior](https://docs.nats.io/learn/jetstream/your-first-stream#the-defaults)

Avoid two hub ingest paths for the same logical event. If a hub stream both captures the device's live republish on `dev.<XUID>.evt.>` and sources the same origin records with that transformed subject, it can store two copies. The source path alone stores records and produces no Core NATS broadcast. Separate live and durable paths remain valid when their storage and listener contracts do not double-ingest. Also, a broad edge capture on `evt.>` can recapture hub traffic after an inbound mapping turns the namespaced subject back into `evt.>`, creating a feedback path that symmetric routing can turn into a loop. Give locally owned capture subjects and inbound sink subjects disjoint contracts, or enforce a tested direction marker and deduplication rule.

### Source consumers, authorization, and identity need ownership rules

In v2.14.4, the default source path creates a server-managed `JS_SRC_*` consumer with flow control, heartbeats, an inactive threshold, and retry scheduling. Removing a source triggers one best-effort delete of an auto-created consumer. A consumer supplied explicitly in the source configuration is reset and reused, and the target does not own its deletion. NATS 2.14 documentation recommends pre-creating explicit consumers where possible. [v2.14.4 setup and retry](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/stream.go#L3899-L4124), [v2.14.4 source update and cleanup](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/stream.go#L2485-L2606), [v2.14.4 best-effort delete](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/stream.go#L2790-L2848), [explicit-consumer protocol](https://github.com/nats-io/nats.docs/blob/f115becf6563e3bbe16bb94cbf87bfceb84199c1/using-nats/jetstream/nats_api_reference.md#L125-L146)

The generated source consumer uses `AckNone` and `MaxDeliver: 1`; its recovery model is sequence-gap detection, recreation, and replay while the origin still retains the record. It is not the relay's per-message end-to-end custody acknowledgement, so the cutover must define when NCDL considers hub custody complete. [v2.14.4 source consumer configuration](https://github.com/nats-io/nats-server/blob/bbd6dc5e903f3505a1d9a7a21c50e0131901afd7/server/stream.go#L3985-L4000)

A same-account, cross-domain leaf source does not require account imports or exports, but routing and permissions must carry the source consumer API or reset request, its reply, flow-control traffic, and the delivery subject. Crossing an account boundary additionally requires matching imports and exports: service types for the API and flow-control paths, and a stream type for delivery. A wrong type can leave replication configured but unable to catch up. Source provenance records the origin stream, sequence, transforms, and original subject; it does not establish the original publishing user's identity. Preserve device identity explicitly in the transformed subject or trusted headers and validate it at the account boundary. [source authorization subjects](https://github.com/nats-io/nats.docs/blob/f115becf6563e3bbe16bb94cbf87bfceb84199c1/using-nats/jetstream/nats_api_reference.md#L100-L146), [source provenance header](https://github.com/nats-io/nats.docs/blob/f115becf6563e3bbe16bb94cbf87bfceb84199c1/nats-concepts/jetstream/headers.md#sources)

## NCDL implementation gap

This is not a configuration-only relay removal today. The deployed controller and runtime pin the fork at v2.14.1, but NCDL currently rejects node-to-hub source edges and prevents a resource edge from also owning the `durableUpstream` buffer. Its resource-edge IR also lacks a subject transform and per-device domain selector, and no hub-source reconciliation path exists. The running device domain is `DN-<PubKey[:14]>`, not the XUID, so the controller needs a trusted XUID-to-domain binding when it creates each source. [controller dependency](/work/amnet/next/controller/go.mod:15), [runtime dependency](/work/amnet/next/ncdl/v2/runtime/go.mod:9), [topology rejection](/work/amnet/next/ncdl/v2/lint/topology.go:609), [resource-edge IR](/work/amnet/next/ncdl/v2/ir/edges.go:194), [device domain](/work/amnet/next/controller/internal/devicenode/clientnode.go:282)

The present relay owns meaningful guarantees: a file-backed 24-hour local buffer and acknowledged, deduplicated hub publishing. Keep it until native source emission/reconciliation exists and parity tests cover destination isolation, outage recovery, headers, identity, deduplication, and cleanup. [current durable buffer](/work/amnet/next/controller/internal/devicenode/durable.go:66)

## Verification boundary

The current fork was exercised at `release/v2.14.7`, HEAD `733a3cf3`. An independent local integration probe confirmed: local `evt.>` delivery remained unchanged while live republish produced the prefixed Core subject; a hub source caught up after a hub restart while the device stayed alive; a source without republish stored the record but produced no Core broadcast; and inbound `ctr.H.evt.cmd` mapped to `evt.cmd` and was re-exported as `dev.XUID.evt.cmd`, confirming the feedback echo but not a complete loop. This probe did not test device restart durability. The v2.14.1 tag was source-checked, not live-tested.

Four targeted current-fork tests also passed: `TestJetStreamStreamRepublishCycle`, `TestJetStreamStreamRepublishMultiTokenMatch`, `TestJetStreamStreamRepublishAnySubjectMatch`, and `TestJetStreamStreamCheckSourcesWithExternal`.

## Recommendation

Keep the device-local file-backed capture stream as the durable boundary. For durable events, use one hub-side source with a subject transform, then optionally republish from that hub target after storage to serve Core listeners; this avoids a duplicate device live leg. A separate device-republish live path plus source-based durable path is also valid when consumers and hub storage do not ingest both copies. Treat account mappings as a local routing contract change and enforce raw-subject leaf denies. Before removing the relay, verify retention against the maximum outage, disjoint ingress/capture ownership, source-consumer cleanup, API/delivery permissions, stable XUID provenance, deduplication, headers, and the acknowledgement point required by NCDL.
